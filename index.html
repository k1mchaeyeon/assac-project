제가 맡은 부분

03제가 한 일

  • assac.cloud 도메인을 Route 53 → CloudFront로 연결하고, ACM 인증서로 원본(ALB)까지 HTTPS 적용
  • WAF: AWS 관리형 규칙(일반 웹 공격, SQL Injection)과 IP당 5분 1,000건 요청 제한, 초과하면 직접 만든 HTTP 429 안내 페이지 응답
  • 외부 ALB는 CloudFront에서 오는 요청만 받도록 막아, WAF를 거치지 않고 원본으로 바로 들어오는 길을 없앰
  • WAF 차단 로그 → CloudWatch Logs 구독 필터 → Lambda(IP·국가·URI 추출) → Discord 알림. 지표 경보·서버 증감·GuardDuty 탐지도 Lambda가 정리해 Discord로 보내도록 연결
  • 담당 리소스를 Terraform 코드로 작성해 팀원들의 코드와 합침

04문제 해결: 캐시 적중률 0.03%

상황7일 동안 CloudFront 요청 46,703건 중 캐시가 응답한 것은 16건(0.03%). 거의 모든 요청이 서버까지 가고 있었습니다.
원인모든 경로가 캐시하지 않는 기본 동작 하나로 묶여 있었고, 애플리케이션 응답에 Cache-Control 헤더가 없었습니다.
조치정적 경로별 캐시 동작을 추가했습니다. 버전 없는 정적 경로는 1시간, 경로에 버전이 있는 /webjars는 24시간, 진료 기록 같은 동적 화면은 캐시하지 않음. 바꾸기 전 설정은 JSON으로 백업해 되돌릴 길을 남겼습니다.
결과적용 후 정적 경로 6곳이 두 번째 요청부터 캐시(Hit from cloudfront)로 응답했고, 동적 화면은 계속 캐시되지 않는 것까지 확인했습니다.

05회고

IP 단위 요청 제한이라 같은 IP를 쓰는 사용자가 함께 차단될 수 있습니다. 낮은 한도에서는 CAPTCHA, 높은 한도에서 차단하는 단계형 규칙으로 개선할 수 있습니다.

알림은 자동으로 오지만, 그게 실제 공격인지 정상 사용자가 몰린 것인지는 결국 사람이 로그를 열어 판단해야 했습니다. 운영 로그를 AI로 먼저 해석하는 방법을 더 공부하고 싶은 이유입니다.
